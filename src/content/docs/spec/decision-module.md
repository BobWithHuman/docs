## 하는 일

Provenance Tracer가 넘긴 Provenance Record만 보고 호출을 통과시킬지, 막을지, 사용자에게 물을지 정한다. 판정에는 Jev를 쓰지 않는다. (확정)

| 경우 | 판정 | 상태 |
|---|---|---|
| 바깥 영향이 없는 호출 | 통과 (기록만) | 확정 |
| 시작점이 USER나 DELEGATED이고 값이 괜찮음 | 통과 | 확정 |
| 시작점이 DOC | 차단 | 확정 |
| 값이 끼워 넣은 것 | 차단 | 확정 |
| 시킨 문단이 숨긴 글 | 차단 | 확정 |
| 시작점이 DOC인데 사용자 요청도 함께 걸렸고, 사슬 확신도가 기준 근처(±0.05) | 사용자에게 묻기 | 확정 |
| 시작점이 ERROR나 SELF | 1차는 기록만 | 확정 |
| UNRESOLVED, 값의 근거 없음 | CLEAN이면 통과, EXPOSED면 묻기 | 확정 |

같은 도구나 명령이 세 번 막히면 사용자에게 알린다. 차단 사유에는 무엇에 걸렸는지가 아니라 무엇을 하면 되는지만 쓴다. 맡긴 문서 자체가 공격일 때(공격자가 이슈 첫 문단에 지시를 쓴 경우)를 막는 최종 방어로, 시작점이 DELEGATED여도 민감한 행동이면 사용자에게 묻는다. (확정)

### 1차 판정 표

10월 10일 평가에는 아래 표로 판정한다. (초안)

| 경우 | 판정 | 상태 |
|---|---|---|
| 바깥 영향 없음 | 통과 | 초안 |
| 시작점이 USER나 DELEGATED이고 값이 괜찮음 | 통과 | 초안 |
| 시작점이 DOC, 끼워 넣은 값, 시킨 문단이 숨긴 글 | 차단 | 초안 |
| UNRESOLVED | CLEAN이면 통과, EXPOSED면 묻기 | 초안 |
| 시작점이 ERROR나 SELF | 기록만 | 초안 |

1차 평가에서는 묻기를 차단으로 센다. (확정) 위의 전체 표와 비교하면 1차 표에는 "사용자 요청도 함께 걸려 묻는" 줄과 "값의 근거 없음" 줄, 그리고 DELEGATED의 민감한 행동을 묻는 규칙이 없다. (초안)

## 받는 것

Provenance Tracer가 만든 Provenance Record를 받는다. (확정)

## 내놓는 것

통과, 차단, 묻기 가운데 하나의 판정과, 차단이면 차단 사유를 PEP에 넘긴다. 노드나 간선을 만들지 않고 Provenance Record의 필드도 채우지 않는다. 기록을 읽기만 한다. (확정)

## Jev 질문

Decision Module은 Jev에 묻지 않는다. (확정)

## 미정

묻기 구간(±0.05)의 가운데가 되는 기준 점수가 무엇인지, "사슬 확신도"가 Record의 "사슬의 최솟값"을 가리키는지 정하지 않았다. 민감한 행동이 무엇인지도 정의되어 있지 않다. 세 번 막힌 것을 어디서 세고 사용자에게 어떻게 알리는지, 한 호출이 표의 여러 줄에 걸릴 때 어느 줄을 먼저 보는지, 사용자에게 묻는 세부 흐름도 남아 있다. ERROR와 SELF를 1차 다음에 어떻게 판정할지도 아직 없다.
